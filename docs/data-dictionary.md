# Data Dictionary — Downloaded File Types & Field Reference

This document describes the three types of files downloaded from S3, their structure, and what each field means.

---

## File Type 1: user_report (CSV)

### What is it?

A daily per-user credit/subscription report generated by the Kiro service at ~2 AM UTC. One CSV per client type per day (e.g., `KIRO_IDE`, `KIRO_CLI`, `PLUGIN`).

### Filename pattern

```
KIRO_IDE_<account_id>_user_report_<YYYYMMDDHHmm>.csv
KIRO_CLI_<account_id>_user_report_<YYYYMMDDHHmm>.csv
PLUGIN_<account_id>_user_report_<YYYYMMDDHHmm>.csv
```

### Local path

```
data/<account_id>/user_report/
```

### Fields

| # | Field | Type | Description |
|---|---|---|---|
| 1 | `Date` | date (YYYY-MM-DD) | The calendar day this row represents |
| 2 | `UserId` | string | IAM Identity Center user ID (format: UUID or `d-<idc_id>.<user_uuid>`) |
| 3 | `Client_Type` | string | Which Kiro surface generated this activity. Values: `KIRO_IDE`, `KIRO_CLI`, `PLUGIN` |
| 4 | `Chat_Conversations` | int | Number of distinct conversation sessions the user started that day via this client |
| 5 | `Credits_Used` | float | Credits consumed from the user's subscription plan for the day |
| 6 | `Overage_Cap` | float | Admin-configured maximum overage credits allowed per month |
| 7 | `Overage_Credits_Used` | float | Credits consumed beyond the plan limit (only counted if overage is enabled) |
| 8 | `Overage_Enabled` | boolean | Whether the admin has allowed this user to exceed their plan's credit limit |
| 9 | `ProfileId` | string | ARN of the Kiro profile this user is subscribed to |
| 10 | `Subscription_Tier` | string | User's plan level. Values: `PRO` (1000 credits/mo), `PRO_PLUS` (2000), `PRO_MAX` (5000) |
| 11 | `Total_Messages` | int | Total messages sent to and received from Kiro (prompts + responses combined) |
| 12 | `New_User` | boolean | `true` if this is the user's first day of activity ever |
| 13 | `User_Email` | string | User's email address (from IdC directory) |
| 14 | `auto_messages` | int | Messages where model was auto-selected by Kiro (no explicit model choice) |
| 15 | `CLAUDE_SONNET_4_20250514_V1_0_messages` | int | Messages using a specific Claude Sonnet 4 release build (PLUGIN client only) |
| 16 | `claude_haiku_4.5_messages` | int | Messages using Claude Haiku 4.5 (lightweight/fast model) |
| 17 | `claude_opus_4.5_messages` | int | Messages using Claude Opus 4.5 model |
| 18 | `claude_opus_4.6_messages` | int | Messages using Claude Opus 4.6 model |
| 19 | `claude_opus_4.7_messages` | int | Messages using Claude Opus 4.7 model |
| 20 | `claude_opus_4.8_messages` | int | Messages using Claude Opus 4.8 model |
| 21 | `claude_opus_5_messages` | int | Messages using Claude Opus 5 model |
| 22 | `claude_sonnet_4_messages` | int | Messages using Claude Sonnet 4 base model (PLUGIN client only) |
| 23 | `claude_sonnet_4.5_messages` | int | Messages using Claude Sonnet 4.5 model |
| 24 | `claude_sonnet_4.6_messages` | int | Messages using Claude Sonnet 4.6 model |
| 25 | `claude_sonnet_5_messages` | int | Messages using Claude Sonnet 5 model |
| 26 | `deepseek_3.2_messages` | int | Messages using DeepSeek 3.2 model |
| 27 | `glm_5_messages` | int | Messages using GLM-5 model (Zhipu AI) |
| 28 | `gpt_5.6_luna_messages` | int | Messages using GPT-5.6 Luna variant |
| 29 | `gpt_5.6_sol_messages` | int | Messages using GPT-5.6 Sol variant |
| 30 | `gpt_5.6_terra_messages` | int | Messages using GPT-5.6 Terra variant |
| 31 | `minimax_m2.1_messages` | int | Messages using MiniMax M2.1 model |
| 32 | `minimax_m2.5_messages` | int | Messages using MiniMax M2.5 model |
| 33 | `qwen3_coder_next_messages` | int | Messages using Qwen3 Coder Next model (Alibaba) |

> **Important: Model columns are dynamic.** Not every CSV has all model columns — they vary by client type (`KIRO_IDE` vs `KIRO_CLI` vs `PLUGIN`), by account (prod vs dev), and by date (new models get added over time). The columns above represent the full superset observed across all downloaded files. A given CSV file will only contain columns for models that were actually used by that client type on that day. Parsers should handle missing columns gracefully (default to 0).

### Key insights from this file

- **Cost tracking**: `Credits_Used` per user per day — who's spending how much
- **Plan sizing**: compare `Credits_Used` against plan limits (PRO=1000/mo) to find under/over-utilized seats
- **Model preference**: which AI models are people actually choosing
- **Adoption**: `New_User` flag tracks when new people start using Kiro
- **Client preference**: are people using the IDE, CLI, or plugin?

## File Type 2: by_user_analytic (CSV)

### What is it?

A daily per-user feature usage report. Shows exactly which Kiro features each person used and how much code was generated, accepted, or rejected. One CSV per day (not split by client type).

### Filename pattern

```
<account_id>_by_user_analytic_<YYYYMMDDHHmm>_report.csv
```

### Local path

```
data/<account_id>/by_user_analytic/
```

### Fields

Grouped by feature area:

#### Identity

| # | Field | Type | Description |
|---|---|---|---|
| 1 | `UserId` | string | Same IAM Identity Center user ID as in user_report |
| 2 | `Date` | date (MM-DD-YYYY) | Calendar day of activity |

#### Chat (conversational AI interactions)

| # | Field | Type | Description |
|---|---|---|---|
| 3 | `Chat_AICodeLines` | int | Lines of code generated by Kiro in chat responses |
| 4 | `Chat_MessagesInteracted` | int | Messages the user interacted with (clicked, copied, applied) |
| 5 | `Chat_MessagesSent` | int | Total messages the user sent to Kiro chat |

#### CodeFix (automated bug fix suggestions)

| # | Field | Type | Description |
|---|---|---|---|
| 6 | `CodeFix_AcceptanceEventCount` | int | Times the user accepted a code fix suggestion |
| 7 | `CodeFix_AcceptedLines` | int | Lines of code accepted from fix suggestions |
| 8 | `CodeFix_GeneratedLines` | int | Lines of fix code Kiro generated (whether accepted or not) |
| 9 | `CodeFix_GenerationEventCount` | int | Times Kiro generated a code fix |

#### CodeReview (AI code review)

| # | Field | Type | Description |
|---|---|---|---|
| 10 | `CodeReview_FailedEventCount` | int | Code review runs that failed (error/timeout) |
| 11 | `CodeReview_FindingsCount` | int | Total issues/findings surfaced by AI code review |
| 12 | `CodeReview_SucceededEventCount` | int | Code review runs that completed successfully |

#### Dev (inline code generation / autocomplete-triggered generation)

| # | Field | Type | Description |
|---|---|---|---|
| 13 | `Dev_AcceptanceEventCount` | int | Times user accepted dev-mode generated code |
| 14 | `Dev_AcceptedLines` | int | Lines accepted from dev-mode generation |
| 15 | `Dev_GeneratedLines` | int | Lines Kiro generated in dev mode |
| 16 | `Dev_GenerationEventCount` | int | Times dev-mode generation was triggered |

#### DocGeneration (AI documentation generation)

| # | Field | Type | Description |
|---|---|---|---|
| 17 | `DocGeneration_AcceptedFileUpdates` | int | Existing files updated with accepted doc changes |
| 18 | `DocGeneration_AcceptedFilesCreations` | int | New doc files created and accepted |
| 19 | `DocGeneration_AcceptedLineAdditions` | int | Lines of documentation accepted |
| 20 | `DocGeneration_AcceptedLineUpdates` | int | Lines of documentation updated and accepted |
| 21 | `DocGeneration_EventCount` | int | Total doc generation events triggered |
| 22 | `DocGeneration_RejectedFileCreations` | int | New doc files created but rejected by user |
| 23 | `DocGeneration_RejectedFileUpdates` | int | Doc file updates rejected by user |
| 24 | `DocGeneration_RejectedLineAdditions` | int | Doc lines generated but rejected |
| 25 | `DocGeneration_RejectedLineUpdates` | int | Doc line updates rejected |

#### InlineChat (AI chat triggered inline in the editor, not the sidebar)

| # | Field | Type | Description |
|---|---|---|---|
| 26 | `InlineChat_AcceptanceEventCount` | int | Inline chat suggestions accepted |
| 27 | `InlineChat_AcceptedLineAdditions` | int | Lines added via accepted inline chat |
| 28 | `InlineChat_AcceptedLineDeletions` | int | Lines deleted via accepted inline chat |
| 29 | `InlineChat_DismissalEventCount` | int | Inline chat suggestions dismissed (ignored/closed) |
| 30 | `InlineChat_DismissedLineAdditions` | int | Lines that would have been added but were dismissed |
| 31 | `InlineChat_DismissedLineDeletions` | int | Lines that would have been deleted but were dismissed |
| 32 | `InlineChat_RejectedLineAdditions` | int | Lines explicitly rejected from inline chat |
| 33 | `InlineChat_RejectedLineDeletions` | int | Line deletions explicitly rejected |
| 34 | `InlineChat_RejectionEventCount` | int | Times user explicitly rejected inline chat suggestion |
| 35 | `InlineChat_TotalEventCount` | int | Total inline chat events (accepted + rejected + dismissed) |

#### Inline (code completions / autocomplete)

| # | Field | Type | Description |
|---|---|---|---|
| 36 | `Inline_AICodeLines` | int | Lines of code generated by inline autocomplete |
| 37 | `Inline_AcceptanceCount` | int | Times user accepted an inline completion (Tab key) |
| 38 | `Inline_SuggestionsCount` | int | Times Kiro showed an inline completion suggestion |

#### TestGeneration (AI test writing)

| # | Field | Type | Description |
|---|---|---|---|
| 39 | `TestGeneration_AcceptedLines` | int | Lines of test code accepted |
| 40 | `TestGeneration_AcceptedTests` | int | Number of test functions/cases accepted |
| 41 | `TestGeneration_EventCount` | int | Times test generation was triggered |
| 42 | `TestGeneration_GeneratedLines` | int | Lines of test code generated (whether accepted or not) |
| 43 | `TestGeneration_GeneratedTests` | int | Number of test functions/cases generated |

#### Transformation (code transformation / refactoring)

| # | Field | Type | Description |
|---|---|---|---|
| 44 | `Transformation_EventCount` | int | Times a code transformation was triggered |
| 45 | `Transformation_LinesGenerated` | int | Lines of code produced by transformations |
| 46 | `Transformation_LinesIngested` | int | Lines of code fed as input to transformations |

### Key insights from this file

- **Feature adoption**: which features are people actually using? (most will be zeros for most users)
- **Acceptance rate**: `Inline_AcceptanceCount / Inline_SuggestionsCount` = how good are Kiro's suggestions?
- **Code generation volume**: `Chat_AICodeLines + Inline_AICodeLines` = total AI-written code per user
- **Review coverage**: `CodeReview_SucceededEventCount` per user = are people running AI reviews?
- **Test generation**: are people using Kiro to write tests? How many get accepted?
- **Rejection signal**: high rejection rates per feature = maybe the feature isn't working well for that user

## File Type 3: prompt_logs (Gzipped JSON)

### What is it?

The full content of every chat interaction — the user's prompt (what they typed) and Kiro's complete response. One file per API request. These are generated in near-real-time (5-minute batching window).

### Filename pattern

```
<account_id>_GenerateAssistantResponse_<YYYYMMDDHHmm>_<random_id>.json.gz
```

### Local path

```
data/<account_id>/prompt_logs/
```

### Structure (JSON, gzipped)

Each file contains one or more records (typically 1-3 per file, batched within a 5-minute window):

```json
{
  "records": [
    {
      "generateAssistantResponseEventRequest": {
        "prompt": "<full user message including context entries>",
        "chatTriggerType": "MANUAL",
        "userId": "d-d0d0d0d0d0.bbbbbbbb-5555-6666-7777-888888888888",
        "timeStamp": "2026-01-15T02:00:05.000000000Z",
        "modelId": "auto"
      },
      "generateAssistantResponseEventResponse": {
        "assistantResponse": "<full Kiro response text including code blocks>",
        "codeReferenceEvents": [],
        "requestId": "11111111-2222-3333-4444-555555555555"
      }
    }
  ]
}
```

### Fields

#### Request (what the user sent)

| Field | Type | Description |
|---|---|---|
| `prompt` | text | The complete prompt including injected context (time, file contents, previous messages). User's actual message is between `--- USER MESSAGE BEGIN ---` and `--- USER MESSAGE END ---` markers. |
| `chatTriggerType` | string | How the interaction was triggered. Known values: `MANUAL` (user typed), others may exist for automated flows. |
| `userId` | string | IAM Identity Center user ID. Format: `d-<idc_instance_id>.<user_uuid>`. Join with `kiro_user_report.user_id` to get email. Note: prompt_logs use prefix format `d-d0d0d0d0d0.bbbbbbbb-...` while user_report stores it without the `d-<idc_id>.` prefix (just `bbbbbbbb-...`) or with a different format (`d0d0d0d0d0-bbbbbbbb-...`). Strip the `d-<idc_id>.` prefix to match. |
| `timeStamp` | ISO8601 UTC | When the request was sent to the model |
| `modelId` | string | Which AI model handled this request. Values: `auto` (Kiro picks), `claude-opus-4.6`, `claude-opus-4.8`, `claude-sonnet-5`, etc. |

#### Response (what Kiro answered)

| Field | Type | Description |
|---|---|---|
| `assistantResponse` | text | Full response text including markdown formatting, code blocks, explanations. This is exactly what the user saw. |
| `codeReferenceEvents` | array | References to open-source code that influenced the response (for attribution/licensing). Usually `[]`. |
| `requestId` | UUID | Unique identifier for this request-response pair. Can be used for deduplication. |

### Prompt structure breakdown

The `prompt` field contains structured sections injected by the IDE:

```
--- CONTEXT ENTRY BEGIN ---
Current time: Saturday, 2026-01-15T12:57:00.000+05:30
--- CONTEXT ENTRY END ---

--- USER MESSAGE BEGIN ---
<actual user input here — could be text, pasted logs, error messages, code>
--- USER MESSAGE END ---
```

In multi-turn conversations, the prompt may also contain previous conversation turns (though typically those are sent as separate context, not visible in this single-record format).

### Key insights from this file

- **What people are asking**: actual questions, problems, debugging sessions
- **Response quality**: see what Kiro answered — was it helpful? accurate?
- **Usage patterns**: are people pasting logs? writing specs? debugging? generating code?
- **Model routing**: when `modelId` = `auto`, what types of prompts go to which models?
- **Security/compliance**: detect if anyone is pasting sensitive data (credentials, PII, production configs)
- **Conversation depth**: how many back-and-forth messages does it take to solve a problem?
- **Code generation**: how much of the response is actual code (inside ``` blocks) vs explanation?

### Derived metrics (for potential DB loading)

| Metric | Derivation | Use |
|---|---|---|
| `prompt_length` | `len(prompt)` in chars | Distribution — are people writing long prompts? |
| `response_length` | `len(assistantResponse)` in chars | Cost/efficiency proxy |
| `has_code_in_response` | contains triple-backtick code block | % of responses that include code |
| `user_message_length` | extract between `USER MESSAGE BEGIN/END` markers | Actual user effort |
| `hour_of_day` | extract hour from `timeStamp` | Peak usage hours heatmap |
| `model_used` | `modelId` field directly | Model distribution pie chart |
| `is_log_paste` | prompt contains stack traces, kubectl output, log lines | % of usage that's debugging vs generation |

## Summary: Three Data Layers

| Layer | File Type | Grain | Volume | Best for |
|---|---|---|---|---|
| **Billing/Capacity** | user_report CSV | 1 row per user × client × day | ~3 files/day | Credits, costs, tier sizing, DAU |
| **Feature Usage** | by_user_analytic CSV | 1 row per user × day | ~1 file/day | Feature adoption, acceptance rates, code volume |
| **Conversations** | prompt_logs JSON.gz | 1 file per API request | ~500-5000 files/day | Content analysis, quality review, compliance |

Each layer answers different questions:
- user_report → "How much is this costing us? Who's using the most?"
- by_user_analytic → "Which features are people using? How effective is the AI?"
- prompt_logs → "What are people actually asking? Is the AI helping?"

## MySQL Table: kiro_prompt_log (prompt log metadata)

Prompt logs are stored in MySQL as **metadata rows** (one per request), not as raw
gzipped files. Populated by `python main.py --account <profile> --prompt-logs`.
Full prompt/response text is optional — stored only when `--store-text` is passed;
otherwise the `*_text` columns are NULL and you read raw content from the `.json.gz`
files (or via `read_logs.py`).

| Column | Type | Source / Derivation | Meaning |
|---|---|---|---|
| `aws_account_id` | VARCHAR(16) | pipeline | Source AWS account (Grafana filter) |
| `account_label` | VARCHAR(32) | pipeline | prod/dev label |
| `request_id` | VARCHAR(64) | `...Response.requestId` | Unique per request (dedupe key) |
| `user_id` | VARCHAR(128) | `...Request.userId` | Raw prompt_log form `d-<idc>.<uuid>` |
| `user_id_normalized` | VARCHAR(128) | derived | Converted to user_report form `<idc>-<uuid>` for JOINs |
| `event_time` | DATETIME(3) | `...Request.timeStamp` | Request timestamp, millisecond precision |
| `event_date` | DATE | derived | `DATE(event_time)` — fast date filtering |
| `model_id` | VARCHAR(64) | `...Request.modelId` | Model used (auto, claude-opus-4.6, …) |
| `chat_trigger_type` | VARCHAR(32) | `...Request.chatTriggerType` | MANUAL, etc. |
| `prompt_length` | INT | `len(prompt)` | Full prompt char count (incl. context) |
| `user_message_length` | INT | derived | Char count between USER MESSAGE markers |
| `response_length` | INT | `len(assistantResponse)` | Response char count |
| `has_code_in_response` | TINYINT(1) | derived | 1 if response contains a ``` code block |
| `code_reference_count` | INT | `len(codeReferenceEvents)` | OSS code references cited |
| `prompt_text` | MEDIUMTEXT NULL | `prompt` | Full prompt (only if `--store-text`) |
| `response_text` | MEDIUMTEXT NULL | `assistantResponse` | Full response (only if `--store-text`) |
| `source_file` | VARCHAR(255) | filename | Original `.json.gz` for drill-down |

**Unique key:** `(aws_account_id, request_id)` — idempotent, safe to re-run.
**JOIN to emails:** `kiro_prompt_log.user_id_normalized = kiro_user_report.user_id`.

Storage: metadata-only ≈ 250 bytes/row (~75 MB for 300k rows). With `--store-text`
≈ 2-3 KB/row. See `docs/queries.sql` Section 23 for ready-made Grafana queries.

## Appendix: UserId Format Differences

The same user's ID looks different depending on which file type you're reading. This matters when you want to correlate a user across file types.

### Format by file type

| Source | Format | Example (same user) |
|---|---|---|
| `user_report` CSV (`UserId` column) | `<idc_id>-<user_uuid>` | `d0d0d0d0d0-aaaaaaaa-1111-2222-3333-444444444444` |
| `by_user_analytic` CSV (`UserId` column) | `<idc_id>-<user_uuid>` | `d0d0d0d0d0-aaaaaaaa-1111-2222-3333-444444444444` |
| `prompt_logs` JSON (`userId` field) | `d-<idc_id>.<user_uuid>` | `d-d0d0d0d0d0.aaaaaaaa-1111-2222-3333-444444444444` |

### Breakdown

```
user_report / by_user_analytic:
  d0d0d0d0d0-aaaaaaaa-1111-2222-3333-444444444444
  ├─────────┘ ├──────────────────────────────────┘
  IdC instance   User UUID
  (10 chars)     (standard UUID with dashes)

prompt_logs:
  d-d0d0d0d0d0.aaaaaaaa-1111-2222-3333-444444444444
  ├┘├─────────┘├┘├──────────────────────────────────┘
  prefix IdC ID  dot  Same User UUID
```

- `d0d0d0d0d0` — your org's IAM Identity Center instance ID (same for all users)
- `aaaaaaaa-1111-2222-3333-444444444444` — the user's unique ID within Identity Center
- `d-` prefix and `.` (dot) separator only appear in prompt_logs

### Converting between formats

| From → To | Rule |
|---|---|
| prompt_logs → user_report | Strip `d-` prefix, replace first `.` with `-` |
| user_report → prompt_logs | Split at first `-` after 10-char prefix, prepend `d-`, replace that `-` with `.` |

### Matching users to emails

`User_Email` only exists in `user_report` CSVs. To find a user's email from a prompt_log record:

1. Take the prompt_log userId: `d-d0d0d0d0d0.aaaaaaaa-1111-2222-3333-444444444444`
2. Convert to user_report format: `d0d0d0d0d0-aaaaaaaa-1111-2222-3333-444444444444`
3. Look up that `UserId` in any `user_report` CSV → get `User_Email`

The `read_logs.py` script handles this automatically when you use `--user <email_substring>`.
